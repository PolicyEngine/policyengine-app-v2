PolicyEngine UK Chat: AI tax and benefit answers grounded in the PolicyEngine model

How PolicyEngine UK Chat pairs a language model with the PolicyEngine UK microsimulation engine

Beta 11 August 2026

What models can and cannot compute

People increasingly ask AI systems what a tax or benefit reform would cost, who would gain, and what a household would actually receive. Language models handle the first half of that job well: they read an ambiguous question, work out what is being asked, and explain the answer in plain English.

They handle the second half badly. Tax and benefit questions need a degree of accuracy that models do not yet offer on their own. The figure has to come from a model whose assumptions can be inspected and verified — not from something that pattern-matches its way to a plausible number.

We have measured this directly. In PolicyBench, an evaluation built on the US tax and benefit system, we scored how accurately AI models compute taxes and benefits from household prompts with no tools and no lookups, against deterministic PolicyEngine outputs. In the launch results the top model — OpenAI's GPT-5.5 — matched PolicyEngine exactly on 80.3% of its scored outputs. Computed amounts were the hardest cases: income tax before credits scored far below eligibility flags, because getting it right means sequencing income concepts, thresholds, exclusions and credits in the correct order.

The finding

The harder the computation, the less a language model can be trusted to do it unaided. The benchmark covers US policy, but the lesson carries directly to the UK.

PolicyEngine UK Chat is built around that finding. It is a conversational interface for UK tax and benefit analysis, now in beta, in which the AI reads the question and the PolicyEngine UK microsimulation model produces every number.

The boundary

The central design decision is where the predictive layer stops and the deterministic layer starts.

The predictive parts are the ones language models are genuinely good at: interpreting wording, deciding which kind of analysis is being requested, drafting the explanation, and suggesting a sensible follow-up. Those tasks are open-ended and language-heavy.

The deterministic parts are the ones users need to be able to check: validating the request, looking up parameters, constructing household inputs, running simulations, computing weighted outputs, and producing chart data. None of these should depend on model memory — and in PolicyEngine UK Chat none of them do. The runtime enforces the boundary instead of asking the model to respect it in a prompt.

When a question is ready for computation, the model receives the calculation tools plus a reference generated from the installed engine — its capabilities and its parameter schema. The model's view of what it can compute is therefore tied to the deployed version of PolicyEngine, not to a hand-written prompt that drifts out of date every time the model changes.

Anatomy of an answer

The clearest way to see the boundary is to follow one question through the system. Take a question with real policy weight and no single obvious lookup: "What's the poverty impact of abolishing the two-child limit?" Six things happen before a number reaches the screen. 1
Route
— the gateway pre-pass
Click to expand

Every turn starts with a cheap classify-and-route pre-pass. The gateway decides what kind of request this is — a rule lookup, a household calculation, a society-wide reform — and grounds the loose parts of the question into slots the rest of the pipeline can use.

It costs a fraction of a full turn and it keeps simple questions from dragging the whole simulation machinery behind them.

~ Model
  • Reads "abolishing the two-child limit" as a reform request
  • Grounds the implied year and population
  • Picks the society-wide pathway over a household one
= Engine
  • Supplies the scope descriptor the gateway routes against
  • Nothing is computed yet
Key insight

Routing is a prediction, so it is allowed to be wrong. Nothing downstream trusts it for a number.

2
Discover
— what can actually be changed
Click to expand

"The two-child limit" is a phrase in the news, not a parameter path. The model has to find the thing in the model that corresponds to it, and it does that by asking the engine rather than by remembering.

Nine discovery tools split the catalogue by area — entities, variables, parameters, reform targets, household inputs, supported outputs — so the model requests only the metadata it needs instead of carrying the whole model in its context.

~ Model
  • Searches reform targets for "two child limit"
  • Reads back the parameter path and its current value
= Engine
  • Returns paths and aliases from the installed UK package
  • Returns the parameter value for the requested year
Key insight

The catalogue is generated from the deployed engine, so a model trained before a policy change still cannot invent a parameter that does not exist.

3
Validate
— fail before you compute
Click to expand

Before anything runs, the proposed reform goes through validate_reform — a flat parameter-path reform checked against the real schema for the year in question. Synthetic households get the same treatment through validate_household.

A bad path fails here, cheaply, with a typed error the model can read and correct. It does not fail silently three steps later inside a number that looks reasonable.

~ Model
  • Proposes the reform as a parameter-path map
  • Reads the error and retries if the path is wrong
= Engine
  • Type-checks paths, values and the year
  • Rejects anything the model made up
Key insight

Validation is the cheapest place in the system to catch a hallucination, and the only place where catching it costs nothing.

4
Simulate
— a handle, not a dataset
Click to expand

run_society_simulation resolves the fixed dataset and materialises a baseline and a reform simulation in memory. What comes back to the model is not data. It is an opaque simulation_id plus metadata.

The pair lives in a turn-local result store owned by the tool execution context. The model cannot inspect the underlying simulation objects, cannot serialise them, and cannot carry the handle into a later turn.

~ Model
  • Requests the simulation and holds the handle
  • Sees metadata only — never a row of survey data
= Engine
  • Builds baseline and reform Simulation objects
  • Stores the pair and returns an opaque handle
  • Computes no fiscal, poverty or decile result yet
Key insight

Handing back a handle instead of an array is what makes the privacy boundary structural rather than aspirational.

5
Derive
— official weighted outputs
Click to expand

The poverty question is answered by compute_poverty_metrics, which retrieves the stored pair and calls PolicyEngine's own UK poverty output classes. Seven derivative tools cover budgetary impact, programme breakdown, deciles, winners and losers, poverty, inequality, and generic weighted aggregates.

These adapters may reshape an official output to fit the tool contract. They are not permitted to call the country microsimulation directly, convert weighted series to raw arrays, or implement survey weighting themselves.

~ Model
  • Chooses which derivative answers the question asked
  • Passes the handle through, unmodified
= Engine
  • Applies survey weights inside policyengine.py
  • Returns baseline, reform and change
  • Stores the result under its own typed handle
Key insight

Every quantitative claim in the final answer traces back to one of these calls. There is no path by which a number reaches the user without one.

6
Chart and answer
— the only part the model writes
Click to expand

generate_chart takes the derivative handle and emits a deterministic chart spec. Eight policy presets — budget waterfalls, absolute and relative decile bars, winners and losers, poverty, inequality, earnings variation — map typed outputs onto fixed rows. The frontend renders those rows and nothing else.

Only then does the model write prose: it states the assumptions, reads out the computed figures, and offers a follow-up. The words are predicted. The numbers inside them are not.

~ Model
  • Picks the preset that fits the derivative
  • Writes the explanation and the stated assumptions
  • Suggests the next question
= Engine
  • Maps the typed output to fixed chart rows
  • Renders missing values as a dash, never as a bar
Key insight

The model is the narrator of the turn, not the source of it.

Design principles

Five rules hold the boundary in place.

Computed, never recalled

The agent does not quote numbers from memory. Every quantitative answer is produced by a tool call against the compiled PolicyEngine UK model and reported straight from the run.

A typed tool surface

There is no model-authored Python execution tool. The model reaches the engine through 21 typed tools with declared schemas, so what it can do is a fixed, reviewable list rather than an open door.

Opaque, turn-local handles

Simulations and derivatives are addressed by handle, not by value. The result store belongs to one chat turn, and the model can neither inspect nor serialise what sits behind a handle.

Reference from the engine

The model's capability and parameter reference is generated from the installed engine rather than hand-written. Upgrade the country package and the model's view of the world updates with it — no prompt drift.

Aggregate-only by construction

The fixed Enhanced FRS dataset is aggregate-only in chat. The serialisation layer rejects raw dataframes outright, so an accidental row-level payload fails closed instead of becoming a tool response.

The tool surface

Society-wide analysis is a lifecycle, not a single call. Each stage hands a typed handle to the next, and the model can only move forward by holding the handle the previous stage produced.

Nothing is inferred, and empty groups stay null rather than becoming a plausible-looking zero.

What you can ask

Five kinds of question are supported today, and they compose: a thread can move from a rule lookup to a household example to a full reform analysis without switching tools.

"What's the personal allowance this year, and where does it start tapering?"

Allowances, rates, thresholds, benefit amounts, limits and tapers are read out of the model's parameter tree for the year you ask about — including the taper points that are easy to state from memory and easy to state wrongly.

"A single parent, two children, earning £28,000 — what do they take home?"

The household is constructed as a synthetic input, validated, and run through the model to produce taxes, benefits and net income under stated assumptions. One household containing one benefit unit per call; more complex arrangements need separate calls.

"How much does raising the personal allowance by £2,000 cost, and who gains?"

Parametric reforms run across the UK population: budgetary impact, programme-level changes, poverty measures, decile impacts, winners and losers, and weighted caseload counts — each from its own derivative tool.

"Show me that by decile."

When a comparison reads better as a picture than as prose, the computed output is mapped onto a deterministic preset. The chart is drawn from the same typed result as the text, so the two cannot disagree.

"And what if I made it £3,000 instead?"

Follow-ups stay in the same thread. The conversation carries the context; the simulation handles do not — each turn re-runs what it needs, so a later answer is never quietly resting on an earlier turn's in-memory state.

The stack

The backend is organised by topic package — each directory owns one concern, and the calculation boundary is one of them rather than a convention spread across the codebase.

Layer Technology
Frontend Next.js 15 and React 19 with Mantine UI, deployed on Vercel
Backend FastAPI on Python 3.13, served as a Modal ASGI app
Agent Anthropic Claude models driven through a streaming tool-use loop
Engine policyengine.py with the policyengine-uk country package
Gateway A cheap per-turn pre-pass that classifies and routes each message
Auth and storage Supabase for auth, Postgres for conversation history
Observability Tracing and metrics across the whole turn

GET /version reports the policyengine.py version and the installed UK country package version, so any answer can be tied back to the exact engine that produced it.

Limitations

Beta

PolicyEngine UK Chat is a modelling tool, not professional advice. It reports what the model calculates under stated assumptions, and results depend on the dataset, the year and those assumptions.

Only the major UK tax and benefit programmes are modelled, so questions about minor or unmodelled provisions may not be answerable at all — which is a better failure than an answer that looks right.

As with any beta, verify important results before relying on them.

The boundary described above constrains where numbers come from. It does not make the model a good judge of which question you meant, and it cannot make the underlying microsimulation say more than its data supports.
